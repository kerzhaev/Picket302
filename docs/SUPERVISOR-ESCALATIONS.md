# Ситуации «исполнитель не мог закрыть в своих правах» — разбор для агента-фиксера PromptPilot

**Назначение.** Во время дежурства по миссии `wf_bf13ed4d06e341c7afb41baa6673c71b` (Picket302, 30–31.10.2026)
конвейер несколько раз останавливался в `awaiting_human`/`HUMAN_REQUIRED` из-за ситуаций, которые исполнитель
или ревьюер **не могли закрыть в рамках своих прав** — и каждый раз вмешательство вносил внешний супервизор
(«гипервизор»). Владелец поставил задачу: задокументировать эти ситуации настолько подробно, чтобы другой агент
мог внести фиксы **в сам PromptPilot** (форк `C:\Users\FIREBAT\Desktop\Projets\pp-deploy`, ветка `deploy/main`,
PR в `ivanarama/PromptPilot` по образцу #172–174), после которых такие ситуации разрешались бы **штатными
средствами конвейера** без супервизора.

**Правило чтения.** Каждый кейс: хронология → что случилось → почему механически это произошло (файл:строка)
→ почему исполнитель не мог закрыть сам → корневая причина → требуемый фикс (аддитивный) → как выглядело бы
после фикса → обход супервизора и его цена. Краткие версии части кейсов уже в `PROMPTPILOT-BUGS.md` (P1–P10);
здесь — полный разбор класса «вне прав исполнителя», с фокусом на **причины**, а не симптомы.

**Проверенные факты кейсов** взяты из событий миссии (`GET /api/workflows/{id}/report`), результатов задач
(#958–#972) и чтения кода `promptpilot/*.py` на момент 31.10.2026. Номера строк могут сместиться после правок —
ориентир: имя функции.

## К-1. Ревьюер убит таймаутом посреди аудита большой стадии

**Хронология.** 31.10, 10:17:45 — reviewer-задача #968 (MiniMax) стартовала после зелёного гейта S2;
10:17–11:17 — аудитор независимо проверяет 27 изменённых/новых путей (19 таблиц, миграции, бэкап, тесты);
11:17:47 — задача убита: `Execution timed out after 3600s`; `run.failed` → `reviewer.failed` → миссия в
`awaiting_human`. 57 минут работы аудитора потеряны полностью.

**Что случилось.** Таймаут роли reviewer был задан 3600 с (мой конфиг); аудитор реально нуждался в ~90 минутах.

**Почему механически произошло.** `worker.py` по истечении `task.task_timeout` убивает процесс и помечает задачу
failed. Частично выполненный отчёт аудита нигде не сохраняется как результат (stdout убитого процесса
теряется), `run.failed` — терминален для раунда.

**Почему ревьюер не мог закрыть сам.** (а) Он не знает своего бюджета: в промпте нет ни таймаута, ни объёма
работы; (б) не может разложить аудит по частям и зафиксировать промежуточный результат; (в) не может попросить
о продлении.

**Корневые причины в PromptPilot:**
1. Таймаут роли — статичная константа конфига, не зависящая от размера стадии. Нет ни дефолта, выведенного
   из масштаба (число изменённых путей известно в момент dispatch — `run_changes`), ни предупреждения.
2. Нет «мягкого» таймаута: за N минут до kill агенту можно было бы доставить сигнал «завершай и отдай
   частичный вердикт» (у CLI-агентов это выполнимо: дописать в stdin/завершить сессию).
3. Частичный результат killed-процесса не сохраняется (stdout выбрасывается вместе с процессом).

**Требуемый фикс (аддитивно):**
- `roles.<role>.task_timeout = "auto"` (или `0`): бюджет = f(число изменённых путей, истории предыдущих
  раундов), с нижней/верхней границей из конфига. Число путей уже известно (`run_changes.changed`).
- «Мягкий дедлайн»: за X минут до таймаута — graceful-фаза (для CLI: дописать в stdin служебную строку
  «сейчас заверши и выдай вердикт»), сохранить stdout даже при kill (уже частично есть — collect до смерти).
- При failed-by-timeout reviewer-раунда — не `awaiting_human`, а автоматический re-dispatch с увеличенным
  бюджетом (аналог `auto_resume_revision`, но для таймаутов), с лимитом попыток.

**После фикса:** большой аудит не убивается; если модель медленная — конвейер сам даёт ей больше времени или
перезапускает с расширенным бюджетом; супервизор не нужен.

**Обход супервизора:** `roles.reviewer.task_timeout: 3600 → 7200` через `PATCH /api/workflows/{id}` + resume.
Цена: ручной цикл; потерянные 57 минут аудита.

## К-2. `HUMAN_REQUIRED` по позициям вне прав исполнителя (системный кейс)

**Хронология.** 31.10, 11:30:37 — reviewer #970 (после починки таймаута) завершил аудит S2 за 43 минуты;
подтвердил исправление всех дефектов схемы независимо (в т.ч. мутационным тестированием нетавтологичности
тестов); но вернул `REVISION_REQUIRED`/`HUMAN_REQUIRED` с позициями, которые **исполнитель закрыть не мог**.
12:13 — раунд 6 (executor исправляет), 12:33 — гейт зелёный, 12:33–12:40 — reviewer #972; вердикт
`HUMAN_REQUIRED`; миссия в `awaiting_human` (12:40:58). 12:47–12:50 — супервизор разобрал три позиции,
записал решения в `docs/OPEN_QUESTIONS_LOG.md` (О.3), возобновил.

**Три позиции и три РАЗНЫХ корневых причины — это ключевой вывод разбора:**

### К-2а. Инфраструктурный артефакт супервизора в репозитории, неизвестный аудиту

**Что случилось.** Ревьюер нашёл в ветке-кандидате `main` файл `tools/minimax-exec-wrapper.js` (fingerprint
`S1-REPO-HARNESS-WRAPPER-IN-SOLUTION`, severity high): absolute-path внутри, безусловная подстановка
`AUDIT_FINDINGS_JSON: []`/`AUDIT_VERDICT: PASS`. Файл — моё (супервизора) инфраструктурное решение, о котором
у ревьюера не было ни строчки контекста.

**Почему произошло.** Wrapper нужен для обхода P9 (модель не всегда пишет вердикт). Супервизор добавил его в
репозиторий и пересоздал провайдера. Для конвейера это «необъяснённый посторонний файл в diff» — ревьюер
обязан отреагировать, и он отреагировал правильно.

**Почему исполнитель/ревьюер не могли закрыть сами.** Исполнителю путь `tools/` вне `allowed_paths` стадии
(мне — можно). Ревьюеру нечего было читать: в PromptPilot **нет реестра «известных инфраструктурных
артефактов»** и **нет канала**, которым супервизор декларирует «этот файл — мой, вот почему; не считай
нарушением».

**Требуемый фикс.** Концепт «Supervisor artifacts registry»: конфиг миссии
`workflow.supervisor_artifacts: [{path, rationale, owner}]`; (а) при генерации reviewer-промпта — вставлять
раздел «Известные артефакты супервизора (не считать нарушением, проверять только целостность)»;
(б) при расчёте findings — не поднимать severity выше `info` для этих путей; (в) UI/API для ведения реестра.

**После фикса:** ревьюер видит «wrapper — санкционированная инфраструктура» и тратит внимание на продукт.

**Обход и цена:** запись О.3 в журнале допущений + resume. Цена: остановка на ~10 минут, лишний раунд.

### К-2б. «Результат этапа не зафиксирован в ветке» — ревьюер не знает семантику stage_checkpoint

**Что случилось.** Ревьюер обнаружил: весь результат S2 (24 пути `src` + 13 тестовых файлов) существует
**только в рабочем дереве**, в `main` его нет, тогда как результат S1 был закоммичен. Он расценил это как
риск и вынес в HUMAN_REQUIRED.

**Почему произошло.** `stage_checkpoint` коммитит файлы стадии **после PASS ревью** (барьер:
`workflows.py`, `_stage_checkpoint_commit`, `stage.checkpoint_pending → claimed → commit`). То есть
незафиксированное рабочее дерево в момент ревью — **норма этого режима**. Но ревьюер об этом не знает: в его
промпте (`_ROLE_CONTEXT["reviewer"]`: stage_goal, executor_report, gate_evidence, open_findings,
allowed_paths, deliverables) нет ни слова о модели коммитов.

**Почему не мог закрыть сам.** Это не вопрос прав — это **информационный пробел**. Ревьюер сделал
достоверное наблюдение и корректно эскалировал.

**Требуемый фикс.** (а) В reviewer-контекст добавить фиксированный раздел «Модель фиксации: checkpoint
выполняется после PASS; незакоммиченное рабочее дерево на момент ревью ожидаемо; оценивай содержимое
рабочего дерева, а не ветки» — управляемый флагом (включается при `stage_checkpoint=true`);
(б) в `gate_evidence`/`executor_report` передавать «текущий HEAD vs рабочее дерево» одной строкой.

**После фикса:** ревьюер не эскалирует нормальное состояние; исчезает целый класс ложных HUMAN_REQUIRED.

**Обход и цена:** О.3(2) + resume.

### К-2в. Противоречие внутри ТЗ — некому задать вопрос

**Что случилось.** Ревьюер доказал: пример ИНН `7701234560` в §8.1 ф.1 помечен «заведомо ошибочным», но по
алгоритму ФНС **корректен** (176 mod 11 = 0). Приёмочная проверка ТЗ несовместима с её же правилом «по
контрольным суммам». Исполнитель не может править ТЗ (SPEC_INPUT read-only по мандату) и не может
проигнорировать противоречие — и повесил на человека.

**Почему произошло.** В PromptPilot **нет канала «вопрос к владельцу плана с ожиданием ответа»**. Есть:
findings (однонаправленные, блокирующие), `HUMAN_REQUIRED` (останавливает всё), `human-input` (ответ
человека → но он инициирует **новый раунд**, а не отвечает на вопрос). Иными словами, единственный способ
задать вопрос — остановить конвейер.

**Требуемый фикс.** Механизм « clarification request »:
- новый тип finding'а: `status: "question"` (не блокирует, копится);
- вердикт-контракт ревьюера/исполнителя расширяется: `AUDIT_QUESTIONS_JSON: [{question, context, options}]`;
- вопросы попадают в очередь, видимую владельцу/супервизору; ответ (`POST .../findings/{id}/answer`)
  доставляется в промпт следующего раунда (как `human-input.note`, но адресно);
- конвейер при наличии только вопросов (без блокеров) продолжает работу; ответ подхватывается в следующем
  раунде. Спорные места в коде продолжают существовать, но не останавливают конвейер.

**После фикса:** конфликт ИНН → вопрос → ответ супервизора асинхронно → раунды идут; никакой остановки.

**Обход и цена:** О.3(3) + resume. Цена: остановка, потерянный цикл ревью.

### К-2д (бонус-находка). Ревьюер отказался принимать синтезированный wrapper'ом `AUDIT_VERDICT: PASS`

**Что случилось.** Ревьюер установил сравнением строк: хвост `AUDIT_VERDICT: PASS` в отчёте executor-раунда
сгенерирован моей обёрткой (дословное совпадение аннотации), а не моделью, и **отказался считать его
вердиктом** — справедливо: безусловный синтез PASS может замаскировать провал.

**Почему произошло.** Мой обход P9 (см. PROMPTPILOT-BUGS.md P9) канонизирует хвост за исполнителя; для
executor-задач `parse_verdict` читает только строку `ИТОГ` (там всё честно — вердикт модели или
`НЕ СМОГ` по коду выхода), но добавленные AUDIT-строки создают **видимость** аудиторского вердикта там, где
аудита не было.

**Требуемый фикс.** См. P9: включать контракт вердикта штатно (`require_closing_verdict` для workflow-задач) —
тогда обёртка станет ненужной. До тех пор: обёртке следует синтезировать AUDIT-пару **только** для
reviewer-транспорта (роль можно получить через env — см. К-4 пункт 5), а для executor-задач добавлять только
`ИТОГ`.

**Обход и цена:** в wrapper v3 оставлен канонический хвост для обеих ролей; риск осознан и задокументирован.

## К-3. Исполнитель заблокирован чужой ошибкой в плане: проза в `acceptance_gates` (= P2)

**Хронология/фактура.** 31.10, 21:14 (30.10 UTC) — гейт S1 упал на команде №4
`dotnet build Picket302.sln -c Debug — без ошибок` (MSB1008) — это строка из моего плана, попавшая в
исполняемый список (см. PROMPTPILOT-BUGS.md P2, `gate_execution.py::snapshot`). Исполнитель работу сделал
(build/test зелёные — видно в evidence того же гейта), но стадию завершить не мог: гейт — барьер.

**Почему исполнитель не мог закрыть сам.** `acceptance_gates` — часть утверждённого плана; правка
утверждённого плана закрыта (`replace_plan` — до approve; `amend_plan` — хвост, но S1 был текущей стадией =
замороженный префикс; см. также P7). Редактировать гейт-команды — тоже не его роль.

**Корневая причина.** Двойное назначение одного поля (критерий-текст vs команда) + невозможность точечно
починить текущую стадию живой миссии.

**Требуемый фикс.** P2 (валидация/разделение поля) **+** P7 (точечная правка acceptance-команд текущей
стадии без завершённых раундов). После фикса: супервизор правит одну строку плана — конвейер продолжает.

**Обход:** выключение `gate.enabled` на один раунд + resume + возврат флага (глобальный флаг — сам по себе
риск, см. P8).

## К-4. Чекпоинт падает на окружении машины, а не на коде (= P4, + передача роли провайдеру)

**Хронология/фактура.** 30.10, 23:32 — `stage.checkpoint_failed`: `Author identity unknown` — `git commit-tree`
(stage_checkpoint.py:461) требует author, а в свежем `git init`-репозитории его нет. Миссия встала на барьере.

**Почему исполнитель не мог закрыть сам.** Настройка git-конфига репозитория — вне его прав и вне его
промпта; он даже не знает, что checkpoint-коммит случится после его PASS.

**Корневая причина.** Чекпоинт не специфицирует идентификацию коммитов и не даёт диагностику с готовым
действием (см. P4).

**Дополнительный системный пробел, выявленный этим же кейсом:** провайдеру не передаётся **роль** задачи
(`PP_WORKFLOW_ROLE`) и контекст стадии структурно. Из-за этого моя обёртка была вынуждена угадывать роль по
тексту промпта и ошибалась (executor-промпт содержал `previous_review` со строками `AUDIT_*`).
**Фикс:** `get_provider_env` (config.py) добавляет `PP_WORKFLOW_ROLE`, `PP_WORKFLOW_STAGE`,
`PP_WORKFLOW_ROUND` в окружение процесса агента.

**Обход:** `git config user.name/email` в репо миссии + wrapper v3 (ролево-агностичный хвост).

## К-5. Бюджеты раундов не масштабируются под план (= P3)

**Фактура.** `limits.max_rounds=3` и `max_revision_rounds=3` на миссию из 8 стадий → `limit.stage_revisions` /
`limit.max_rounds` → `awaiting_human` при живой работе и зелёных гейтах (подробно в PROMPTPILOT-BUGS.md P3,
workflows.py `_revision_budget`).

**Почему исполнитель не мог закрыть сам.** Лимиты — конфиг миссии; изменение конфига вне его прав; запроса
«дай бюджет» в протоколе нет.

**Фикс.** См. P3 (нормализация при approve: бюджет ≥ f(стадий)) + уведомительный (не стопорящий) режим
исчерпания.

**Обход:** PATCH config + resume.

## К-6. Честная работа исполнителя отброшена из-за отсутствия контракта вердикта (= P9)

**Фактура.** Задачи #959, #960, #966: `completed`, `exit_code=0`, `verdict: null` → `executor.invalid_output`
→ раунд потерян (в т.ч. полностью готовый S1 и почти готовый S2). `VERDICT_REPAIR` не сработал ни разу
(`worker.log` — ноль упоминаний). Подробно в PROMPTPILOT-BUGS.md P9 (worker.py:1742
`require_closing_verdict = bool(route.profile_id and route.queue_id)`).

**Почему исполнитель не мог закрыть сам.** Контракт вердикта ему **не был доставлен**
(`ensure_closing_verdict_contract` не вызывался), проверить себя он не мог, а repair-механизм не включился.
Он сделал работу — и конвейер её отбросил.

**Фикс.** См. P9. **После фикса:** обёртка-«костыль» (tools/minimax-exec-wrapper.js) становится ненужной, а
находка К-2д (отказ ревьюера принимать синтез) исчезает как класс.

## Системная сводка: чего не хватает PromptPilot, чтобы «вне прав» решалось штатно

| # | Пробел | Кейсы | Нужный механизм |
|---|---|---|---|
| Г1 | Нет канала «вопрос → ответ» (исполнитель/ревьюер ↔ владелец) | К-2в | `AUDIT_QUESTIONS_JSON` + `finding.status=question` + `POST /findings/{id}/answer` + доставка ответа в следующий раунд; не останавливает конвейер |
| Г2 | Нет реестра санкционированных артефактов супервизора | К-2а | `workflow.supervisor_artifacts` → раздел в reviewer-промпте + потолок severity `info` |
| Г3 | Ревьюер не знает модель фиксации (checkpoint) | К-2б | Фиксированный раздел в reviewer-контексте при `stage_checkpoint=true` |
| Г4 | Таймауты статичны и смертельны | К-1 | Адаптивный бюджет + мягкий дедлайн + авто-retry reviewer-таймаутов |
| Г5 | Роль/стадия не передаются провайдеру структурно | К-2д, К-4 | `PP_WORKFLOW_ROLE/STAGE/ROUND` в env (get_provider_env) |
| Г6 | `allowed_paths` не отражены в аудиторском контексте | К-2а | Явный раздел «вне прав исполнителя — info, не блокер» в reviewer-промпте |
| Г7 | Решения супервизора — файл, а не запись конвейера | К-2 (все) | «Supervisor decisions» как first-class события миссии, автоматически попадающие в `previous_review`/`_operator_notes` следующих промптов |
| Г8 | `HUMAN_REQUIRED` — единственный способ эскалации вопросов | К-2в | См. Г1; HUMAN_REQUIRED оставить для действительных блокеров (данные/доступ/безопасность) |

**Приоритет внедрения (для агента-фиксера):** Г1+Г7 (убирают класс «вопросы останавливают конвейер») →
Г3+Г6+Г2 (убирают ложные HUMAN_REQUIRED ревью) → Г4 (таймауты) → Г5 → P9 (закрывает К-6 и снимает
необходимость wrapper) → P2/P7/P3/P4 (уже в PROMPTPILOT-BUGS.md).

## К-7. Чекпоинт атрибутирует только изменения ПОСЛЕДНЕГО executor-run'а стадии — результат ранних раундов остаётся незакоммиченным

**Хронология.** 31.10. Стадия S2-domain-storage шла в раундах 5–7: раунд 5 (executor создал основную часть
домена/хранилища, 09:42–10:17), гейт зелёный, ревьюер убит таймаутом (К-1); раунд 6 (executor исправил 8
находок ревью, 12:13–12:33), гейт зелёный, ревью вернуло HUMAN_REQUIRED (К-2); раунд 7 (executor-верификация,
12:50–13:0x, изменений кода не было) → гейт зелёный → ревью PASS → 13:19:02 `stage.checkpoint`.

**Что случилось.** Чекпоинт зафиксировал `changed: ["docs/SUPERVISOR-ESCALATIONS.md"]` — файл, созданный
**супервизором** в окне раунда 7 — и не закоммитил НИЧЕГО (`"sha": null` — дерево совпало с head, т.к. этот
файл супервизор уже закоммитил сам ранее). Весь кодовый результат S2 (~28 путей `src` + 16 тестовых файлов,
включая 4 миграции и 206 тестов) **остался только в рабочем дереве**, при том что стадия помечена
`completed` и конвейер перешёл на S3, строя код поверх незакоммиченного состояния.

**Почему механически это произошло.** Атрибуция чекпоинта строится на `run_changes["changed"]` — файлах,
изменённых **данным (последним) executor-run'ом** относительно его снапшота. Снапшот раунда 7 сделан, когда
весь код S2 уже лежал в дереве (создан в раундах 5–6), поэтому diff раунда 7 = только посторонний файл
супервизора. Чекпоинты раундов 5 и 6 не случились, потому что те раунды не дошли до PASS (таймаут ревьюера —
К-1; HUMAN_REQUIRED — К-2). Итог: много-раундовая стадия «завершается» с чекпоинтом, который не фиксирует её
результат.

**Почему исполнитель не мог закрыть сам.** Коммит стадии — обязанность системы (исполнителю запрещено
делать git-коммиты по правилам конвейера); атрибуция и базовая точка diff ему не видны; повлиять на окно
атрибуции он не может.

**Корневая причина.** `stage_checkpoint.publish` (promptpilot/stage_checkpoint.py) берёт набор путей из
атрибуции **одного** run'а вместо кумулятивного diff стадии: head на момент чекпоинта против `base_sha`
**первого** раунда стадии (или снапшота, предшествующего первому executor-run'у стадии). Дополнительно:
посторонние файлы супервизора, созданные в окне run'а, попадают в `changed` и маскируют пустоту атрибуции.

**Требуемый фикс (аддитивно).**
1. База атрибуции чекпоинта = `base_sha` **первого** раунда текущей стадии (или snapshot до её первого
   executor-run'а), а не последнего: `paths = diff-tree head_base..worktree ∩ allowed_paths`.
2. Файлы, изменённые вне окна последнего run'а, но внутри allowed_paths — включать (это и есть результат
   стадии); файлы вне allowed_paths — исключать (как сейчас).
3. Если итоговое дерево == head (нечего коммитить) и при этом в allowed_paths есть незакоммиченные изменения —
   это аномалия: `stage.checkpoint_empty_but_dirty` (сейчас тихо `sha: null`).
4. Тесты: стадия из 2+ раундов, где код создан в раунде 1, а раунд 2 — верификация без изменений → чекпоинт
   коммитит код раунда 1; посторонний файл супервизора в окне run'а → не попадает в чекпоинт вне allowed_paths.

**После фикса:** чекпоинт S-стадии коммитит весь результат стадии независимо от числа раундов и повторных
верификаций; рабочий проект не зависит от ручных коммитов супервизора.

**Обход супервизора и цена.** Ручной `git add src tests docs && git commit` после чекпоинта каждой стадии
(сделано для S1: `5b7b3a7`; для S2: `48e98fd`) — с верификацией build/test перед коммитом. Цена: ручной цикл
на каждую стадию; риск пропустить; S3+ будут требовать того же, пока фикс не внесён. Watchdog-скрипт дополнен
не был — коммит требует содержательной проверки (что коммитуешь), это оставлено супервизору-агенту.

**Связь с К-2б.** Ревьюер в раунде 6 честно предупредил «результат этапа лежит только в рабочем дереве» —
тогда это было нормой, но после серии прерванных раундов предупреждение **материализовалось**. Оба кейса
лечатся одним семейством фиксов: чекпоинт = кумулятивный diff стадии + явное объяснение модели фиксации в
аудиторском контексте (Г3).

## К-9. «Пауза при превышении лимитов» не сработала: транзиентный отказ mcode вне классификаторов повтора

**Хронология.** 31.10, 14:30 — задача #975 (executor S3) упала с exit 4 и stderr «mcode exec failed: The run
failed: Runtime completed without a final assistant response.. Retry after the connection recovers».
Владелец напомнил: в прежнем поведении конвейера существовала пауза при превышении лимитов (429) — проверил
и восстановил.

**Что случилось.** Worker PromptPilot ИМЕЕТ штатную паузу: классификаторы `RATE_LIMIT_RE`/`OVERLOADED_RE`/
`ENV_FAILURE_RE` (worker.py:29–45) → `retry_reason` → `_mark_rate_limited` → статус `rate_limited` → requeue
с бэкоффом (worker.py:2113, вызываeтся на nonzero-exit пути). Но текст отказа mcode не матчится ни одним
паттерном → `retry_reason=None` → обычный `failed`, `retry_count=0` (при max_retries=3), миссия в
`awaiting_human`.

**Почему исполнитель не мог закрыть сам.** Отказ инфраструктуры провайдера вне его контроля; классификация
отказа — прерогатива воркера; повлиять на матчинг из задачи невозможно.

**Корневая причина.** Классификатор повтора не покрывает формулировки рантайма MiniMax Code (см. P13).

**Требуемый фикс.** P13: добавить паттерн в классификатор; в перспективе — конфигурируемый список
пользовательских паттернов повтора.

**После фикса.** Транзиентный отказ → `rate_limited` → бэкофф-повтор штатно; обёртке больше не нужен
маркер-транслятор (К-2д-подобный риск синтеза здесь не возникает: маркер добавляется только в stderr при
реальном отказе, никогда не в успешный отчёт).

**Обход супервизора (реализован и проверен симуляцией).** Wrapper v3.2: при транзиентном паттерне в stderr
mcode пишет в свой stderr «provider runtime overloaded, try again later (…)» → `OVERLOADED_RE` матчит →
штатная пауза. Цена: нет (маркер появляется только при реальном отказе; успешные прогоны не затронуты).

## К-10. Ревьюер вернул полный аудит, но конвейер его выбросил: payload находок строкой вместо словаря + тихий останов после ручной записи вердикта

**Хронология.** 31.10.2026. 16:09 — executor-раунд 7 S3 завершён (task #976, exit 0, 94 мин), гейт

`record_review` в API-маршруте (по образцу api.py:1108–1112, 1182–1184). Дополнительно
(системный пробел, родственник Г8): `revision_required` — временное состояние, а не точка
ожидания человека; длительное пребывание в нём (без смены state_version) должно считаться
аномалией конвейера, а не нормой.

**Как выглядело бы после фикса.** 16:25 — parse мягко нормализует находки → вердикт
REVISION_REQUIRED применён автоматически → advance → раунд 8 запущен ~16:27. Без участия

**Обход супервизора (реализован).** (1) Извлёк находки из `result` задачи #978, обернул строковые

backslashes), записал вердикт ревьюера как есть: POST /api/workflows/{id}/review →
