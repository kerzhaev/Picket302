# RC S41 — Клиент-сервер, общая БД (№127): архитектурный документ для решения владельца

Дата: 2026-11-14. Base `31d8e70`. Функция 127 (ТЗ §8.8) помечена **[К]** —
решение владельца (S01 строка 101: «SQLite-only vs PostgreSQL»). Этап
выполняет свою достижимую часть: архитектурный документ с вариантами,
текущей готовностью и последствиями каждого выбора. **DONE не присваивается**
— флаг `OWNER_DECISION_REQUIRED` остаётся до явного решения владельца
(S42–S45 зависят от него и не стартуют).

## 1. Текущая готовность (что уже есть)

| Компонент | Состояние | Где |
|---|---|---|
| Реестр серверов БД | ГОТОВ (функция 101) | `Infrastructure/Persistence/ServerRegistry.cs` |
| Диагностика «сервер БД не запускается» | ГОТОВ (функция 136, S35) | `DbServiceDoctor` + `FormDbServiceDoctor` |
| Диалектный слой запросов | ГОТОВ: каждый query.xml содержит ОБЕ команды (Sqlite + PostgreSql), валидатор параметризован диалектом | `Templates/Queries/*.xml`, `QueryDialects`, `SqliteReportDataProvider` |
| Поставка/миграции | SQLite-only: `MigrationRunner` + `SqliteUnitOfWork`; PostgreSQL-провайдера НЕТ | `Infrastructure/Data` |
| Драйвер PostgreSQL | НЕТ (не подключён, пакет не в зависимостях) | — |

Вывод: диалектный слой уже двуязычен (12 query.xml × 2 диалекта проверены
S36-эрой тестами инвентаризации) — это осознанная заделка под №127, но
исполнительной части (драйвер, миграции, сессия) под PostgreSQL нет.

## 2. Вариант A — SQLite-only (упрощение поставки)

**Суть**: функция 127 закрывается как «реестр серверов + диагностика
оставлены (функции 101/136), клиент-серверная СУБД не входит в поставку».

| За | Против |
|---|---|
| Нулевая разработка: всё существующее сохраняется | ТЗ §8.8 ф.127 в части общей БД не выполняется (открытое отклонение с подписью владельца) |
| Поставка и обновление (№163) не усложняются — один файл БД | Многопользовательский режим (общая база на сервере) недоступен |
| Резервное копирование (№72) и миграции протестированы именно на SQLite-файле | PostgreSQL-задел в query.xml остаётся неиспользуемым (не вредоносно) |
| CLEAN_MACHINE_INSTALL упрощается (S49) | — |

**Последствия для RC**: S42–S45 закрываются как NOT_APPLICABLE_BY_OWNER;
№127 получает формулировку «частично реализовано по решению владельца» в
финальном отчёте. Флаг: `OWNER_DECISION=SQLITE_ONLY`.

## 3. Вариант B — PostgreSQL-клиент-сервер

**Суть**: полноценный клиент-сервер: драйвер Npgsql, миграции PG-диалекта,
`PgUnitOfWork`, подключение через реестр серверов (функция 101 уже даёт
выбор сервера), диагностика (136) расширяется pg_isready-подобной проверкой.

| За | Против |
|---|---|
| ТЗ §8.8 ф.127 выполняется полностью | Оценка: драйвер+миграции+сессия+блокировки = 3–5 полных волн (S42–S45 уже заложены) |
| Задел query.xml немедленно используется | Требуется PG-сервер на стенде для приёмки (сейчас нет — CLEAN_MACHINE NOT_RUN) |
| Общая база — реальная многопользовательская работа | Миграции SQLite→PG (перенос данных) — отдельная волна |
| — | Резервное копирование/восстановление №72 переписывается под pg_dump/pg_restore |
| — | Риски параллелизма/блокировок в репозиториях (сейчас INSERT-only паттерны на SQLite) |

**Последствия для RC**: финальная сборка (S50) отодвигается на ≥4 волны;
текущие 1555 тестов SQLite-стенда остаются валидными (diалектный слой
изолирован), но потребуют PG-дублей интеграционного уровня.

## 4. Вариант C — гибрид (SQLite локально + PG опционально в Pro-редакции)

Связка с №126 (редакции): Professional получает PG-подключение. Наиболее
близко к тексту ТЗ, но включает ВСЕ риски варианта B плюс продуктовую
дифференциацию (гейты редакций, тесты лимитов).

## 5. Рекомендация координатора (НЕ решение)

По состоянию кода (SQLite-стенд полностью приёмочен, PG-контур нулевой,
CLEAN_MACHINE NOT_RUN) минимальный риск для RC текущего цикла — вариант A
с явной подписью владельца под отклонением и переносом B в следующую
версию. Решение — за владельцем.

## 6. Формат решения владельца

Ответ одним из вариантов в произвольной форме (достаточно «A»/«B»/«C» +
комментарий): `OWNER_DECISION=SQLITE_ONLY` / `OWNER_DECISION=POSTGRESQL` /
`OWNER_DECISION=HYBRID_PRO`. До получения — S42–S45 не стартуют,
`OWNER_DECISION_REQUIRED` сохраняется в реестре S01 §6.

## 8. Дополнение 2026-11-14: вариант D — локальная SQLite + серверная служба

Задание от 2026-11-14 («настоящий совместный режим для 1–5 рабочих мест») прямо
запрещает в этой волне установку и реализацию PostgreSQL и требует сохранить
существующий одиночный режим полностью. Поэтому варианты A/B/C выше не
отменяются, а дополняются четвёртым — тем, который фактически выбран для
реализации.

**Суть варианта D.** Одиночный режим сохраняется как есть (локальная SQLite
на ПК пользователя, без службы и сети). Для совместной работы на одном
офисном Windows-компьютере устанавливается **отдельная серверная служба
Picket302**; только она открывает SQLite-файл, лежащий на **локальном диске**
этого компьютера. Клиентские приложения (до пяти) обращаются к службе через
типизированный API — **не** по SMB/UNC к файлу базы и **не** через прямой
SQL-порт. Порт по умолчанию — `30242/TCP` (не 5432, чтобы не пересекаться с
PostgreSQL). Серверный ПК может быть обычным компьютером сотрудника; при его
выключении общая база временно недоступна, и клиенты не переходят молча на
местные базы.

| За | Против |
|---|---|
| Ноль внешних СУБД: используется существующий стек проекта (`Microsoft.Data.Sqlite` + Dapper + `MigrationRunner`), те же доменные правила и те же репозитории | Появляется новый исполняемый проект (служба), контрактный слой и отдельный установщик |
| Существующий `BackupService` (`VACUUM INTO`) пригоден без изменений | Нужен собственный протокол, маркировка версий общих сущностей и идемпотентность команд |
| Поставляется как обычная служба Windows, без лицензий и администрирования СУБД | SQLite рассчитан на небольшое число писателей — при 5 клиентах требуется измерить |
| Один компьютер сотрудника вместо серверного оборудования | Общая база недоступна, когда серверный ПК выключен (это осознанное свойство режима) |

**Важно: вариант D — это не PostgreSQL.** Драйвера PostgreSQL, PG-миграций и
`PgUnitOfWork` в проекте по-прежнему нет, и настоящий документ не заявляет их
наличие. Вариант D — отдельная архитектурная запись со своим контрактом,
службой и установщиком.

Полная карта исходного кода (какие сценарии общие, какие локальные, какие
сознательно недоступны в общем режиме) и подробный ADR — в
`docs/shared-service-2026-11-14/S00-source-map.md`. Фактические результаты
реализации и испытаний — в итоговом отчёте владельцу этой волны.
