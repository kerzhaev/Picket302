# RC S12/S13 — Диагностика SCM и решение по исправлению COM

Дата: 2026-11-12. Код `46794c1`→`881f077`. Основание: S11 (холодная
активация PASS) + приёмка 5× (S14).

## S12 — Диагностика SCM

Симптом Stage4 (`0x80040154` REGDB_E_CLASSNOTREG за ~43 мс **без попытки
запуска процесса**, без новой записи `-Embedding`) на текущем коде RC из
документированного чистого состояния **НЕ воспроизводится**: 6 холодных
активаций (1 baseline S11 + 5 приёмочных S14) дали `hr=0x00000000`,
новый PID сервера, `-Embedding` в дельте журнала, `CoRegisterClassObject
hresult=0x00000000`, `cwd=C:\WINDOWS\system32` (признак запуска именно SCM).
Новых событий Microsoft-Windows-DistributedCOM ни в одном цикле нет.

Категория отказа Stage4 — **B′ (загрязнение SCM)**: кэшированная запись о
сервере, который ещё «держит класс», после жёсткого kill без
`CoRevokeClassObject`; последующие холодные активации отклоняются быстро и
без запуска. Состояние снимается штатным revoke/перерегистрацией. Это
согласуется с собственным комментарием `ComServerHost.ShutdownEventName` и
выводом stage5-verify (8/8 циклов из чистого состояния, включая UNC).

Граница честности: ретроспективно доказать конкретное загрязнение Stage4
невозможно (процессы и кэш SCM не сохранены). ProcMon/ETW-трасса не
снималась, поскольку отказ не воспроизводится (требование S12 «при
воспроизведённом 0x80040154» не наступило). Минимальный воспроизводимый
случай загрязнения: kill сервера без CoRevoke → немедленная холодная
активация; намеренно НЕ выполнялся (правило «Kill = провал прогона»,
риск оставить грязное SCM-состояние в общей среде).

## S13 — Решение по исправлению

Причина установлена как загрязнение SCM, а не дефект приложения.
**Изменений продуктового кода не требуется**: per-PID shutdown-событие
(`Local\Picket302.ComAutomation.Shutdown.<pid>`) и graceful
`CoRevokeClassObject` уже реализованы (stage3.x) и подтверждены всеми
6 циклами (GRACEFUL_EXIT_0 + revoke в журнале). Изоляция по PID соблюдена.

Переход HKCU→HKLM **не требуется и не выполнялся**: per-user модель
`HKCU\Software\Classes` работает без прав администратора и подтверждена
холодной активацией. Решение о смене модели регистрации (если понадобится
для машинной установки) — за владельцем (S15, поставочная модель).

```text
COM_DIAGNOSIS: symptom Stage4 not reproducible from clean state (category B' SCM pollution)
COM_CODE_FIX_REQUIRED=false (per-PID shutdown + graceful revoke already present)
HKCU_TO_HKLM_MIGRATION=not required; owner decision deferred to S15
```

## Замечание D-S14-logenc (P3, косметическое)

`com-automation.log` пишется с двойной кодировкой кириллицы («Запуск» →
«╟ряєёъ», «выполнен» → «т√яюыэхэ»): ASCII-маркеры (pid, -Embedding,
CoRegisterClassObject, CoRevokeClassObject, hresult) целы, кириллические
слова искажены. Из-за этого PowerShell-критерии приёмки, матчившие
кириллицу (`Запуск:`, `выполнен:`), дали ложные `freshEmbedding=False` /
`gracefulRevoke=False`; содержательная проверка по ASCII-маркерам
(encoding-independent, `acceptance-5x-verified.json`) подтвердила все
5 циклов. Дефект кодировки журнала — предсуществующий, на функцию COM не
влияет; кандидат в бэклог (исправление кодировки AutomationServerLog).
