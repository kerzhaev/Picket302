## 3. Этап 1: закрытие пробелов (коммиты 2809e7d, 29212f4)

### 3.1. Связь шаблона с пакетом .lbk

- Миграция `V013__add_template_package_binding.sql`: `print_templates`
  получает `package_id/package_version/package_hash`, `print_history` —
  `operation_id` с индексом.
- `templates.save` проверяет по серверу, что пакет существует, и записывает
  его действующую версию и SHA-256; пустая привязка из запроса не затирает
  сохранённую.
- `templates.upload-package` переводит привязанные строки шаблона на новую
  версию пакета в той же транзакции.
- Клиент (`SharedTemplatePackageResolver` + кэш) получает содержимое по
  привязке; кэш отдаёт только версию с совпадающим отпечатком, повреждённая
  копия заменяется, несовпадение — отказ с понятным сообщением
  (`TemplatePackageUnavailableException`), а не печать по чужому макету.
- Тесты: 4 через настоящий HTTP+TLS (связывание, переход версии, отказ на
  несуществующий пакет), 5 на получатель содержимого (кэш, инвалидация,
  порча, несовпадение отпечатка, шаблон без пакета).

### 3.2. Исходы печати

- Доменное перечисление `PrintOutcome` (Prepared/Spooled/Error/Unknown)
  связано с `PrintEventOutcome` явным соответствием в обоих направлениях
  (не приведением типа).
- Исходы теперь производятся: успешная печать — Spooled; отказ спулера —
  Error; блокировка по размеру — Prepared (задание не передавалось);
  неизвестный исход записи сессии — Unknown.
- **Неизвестный исход не превращается в ложное «не напечатано»**: при
  потере ответа на запись сессии печатный конвейер останавливается до
  спулера с сообщением «печать не выполнялась… повторная печать не
  требуется»; сбой записи журнала после состоявшейся печати оставляет итог
  успешным и предлагает повтор записи без физической печати. Автоматической
  повторной печати нет нигде.
- Журнал печати хранит исход, устройство и безопасный идентификатор
  операции (без секретов; снимки адресов — прежнее правило снимков).
- Тесты: 5 (успех/ошибка/blocked/unknown/сбой журнала), плюс серверная
  проверка записи через HTTP+TLS.

### 3.3. Импорт

- Шаг слияния вынесен за `IImportMerger`: одиночный режим — локальная
  служба, совместный — серверная команда `import.merge` одной командой в
  одной транзакции (стейджинг разбора/проверки остаётся на рабочем месте,
  файл не переносится).
- Мастер импорта в общем режиме больше не гейтится: категории — общая
  база, применение — серверная команда, повтор с прежним идентификатором
  операции не создаёт дублей; применение сделано асинхронным.
- Сервер отклоняет пустой пакет («успешно, ничего не импортировано»
  скрывало бы неверный файл); ответ команды дополнен числом ошибок и
  неподтверждённых записей.
- Тесты: 5 через HTTP+TLS (видимость обоим клиентам, повтор без дубля,
  несовпадение тела → idempotency-mismatch, пустой пакет, некорректная
  схема запроса), 2 на мастер.

### 3.4. COM-автоматизация (запрет тихого fallback)

- Регрессия: проверка сопряжения искала в shared.json имена свойств в
  camelCase, а оболочка пишет PascalCase — отказ не срабатывал никогда, и
  COM-сервер открывал устаревшую локальную базу на сопряжённом ПК.
- Исправлено единым классом `SharedWorkstationMode` (слой
  Infrastructure): JSON-разбор без учёта регистра имён; имя файла реквизитов
  задаётся одной константой.
- Тесты: 4; отказ проверен в обе стороны (со старым правилом тесты падают,
  с новым — проходят).
- Мутации реестров/описей/документов серверными командами **не**
  добавлялись (см. §2, класс A-позже): область чтения осталась SHARED,
  записи — одиночный режим через COM, в общем режиме — гейт.

### 6.2. Лицензирование: доказанная причина 16 падений

S50 объясняла 16 падений истёкшей лицензией машины. Проверка гипотезы
диагностическим прогоном дала **другую, доказанную** причину — дефект
тестовой изоляции:

1. `LicenseStateMachine` при «пустом» реестре берёт
   `LicensingRegistry.Windows()` — реальный HKCU, а не реестр хранилища.
2. AppServices всегда создавал автомат с «пустым» реестром → состояние
   пробного периода читалось из реального HKCU даже под изолированным
   тестовым профилем.
3. HKCU этой машины содержит `TrialStartedAt=2026-11-04` (11 дней при
   сроке 10) → «Пробный период закончился» в 16 тестах, создающих записи
   и печатающих партии.

Чистое доказательство: в изолированном профиле до исправления — блокировка
создания записей при отсутствии файла состояния профиля (значит, источник —
HKCU); после исправления — свежий пробный период (файл профиля,
`TrialStartedAt`=момент запуска), создание разрешено, рассылка создаётся и
видна; реальный HKCU не читается и не изменяется. Системное время,
HKCU-лицензия и производственные проверки не менялись.

Исправление изоляции: у непроизводственного профиля (каталог отличен от
производственного) лицензирование ведётся в файле профиля; реестр продётся
в MachineIdentity, LicenseStore и автомат; производственный профиль —
без изменений (ветка HKCU, срок 10 дней, ворота — не ослаблены).

**LICENSE_TEST_VERIFIED = true**: полный набор Debug **1784/1784**,
Release **1784/1784** (BASE 1639: 1623 pass / 16 fail; dc1ceb4: 1755,
16 fail — те же). Все 16 исторических падений проходят:
11 DistributionPrintScenarioTests, 4 FormDistributionEditorEditingTests,
1 MainShellDistributionActionsTests (полный список имён — в TRX
`tests/Picket302.Tests/TestResults/wave2.trx` и `debug2.trx`).
Один разовый сбой Debug в параллельном прогоне не воспроизвёлся повторным
