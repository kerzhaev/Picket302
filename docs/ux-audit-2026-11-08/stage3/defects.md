## UX3-01

- **ID:** UX3-01
- **Severity:** P0
- **Screen/flow:** Выбор клипарта (`FormClipartPicker`) — открытие диалога
- **Reproduction:** Открыть «Выбрать клипарт» в главном окне (или любой показ формы). WinForms `ImageList` читает добавленные изображения отложенно — при создании дескриптора ListView на первый показ. `ЗаполнитьКаталог` добавляла в ImageList рисунок, привязанный к `MemoryStream`, и уничтожала его (`using`) в конце итерации. На показе формы `ImageList.CreateBitmap` читал уничтоженный Image.
- **Expected:** Диалог открывается, 10 элементов каталога со значками доступны.
- **Actual:** `System.ArgumentException: Parameter is not valid` (`Image.get_Width` ← `ImageList.CreateBitmap` ← `ListView.OnHandleCreated`). В testhost — падение; в harness — модальный диалог исключения, блокирующий поток UI (зарегистрирован пользователем, PID 119900).
- **Evidence:** стек исключения из testhost и UiAcceptance (зафиксирован в этом раунде); зонд `_ProbeClipart` (ctor 48 мс → `Show()` не возвращается); существующие тесты дефект не ловили, т.к. не вызывали `Show()`.
- **Root cause:** Нарушение собственного идиома проекта (прокомментировано в `ОбновитьПредпросмотр`: «GDI+ требует держать поток открытым всё время жизни Image») — в `ЗаполнитьКаталог` копия не создавалась.
- **Changed files:** `src/Picket302.App/UI/Forms/FormClipartPicker.cs` (`ЗаполнитьКаталог`, поле `_значкиДляОсвобождения`, override `Dispose`).
- **Fix:** В ImageList добавляется отвязанная копия `new Bitmap(источник)`; копии держатся в поле формы и освобождаются в `Dispose(bool)` (повторная утилизация безопасна).
- **Regression test:** `FormClipartPickerTests.Диалог_ПоказФормы_ЗначкиДоступныПослеСозданияДескриптора` — показывает форму, проверяет `IsHandleCreated` и равенство ImageList.Images == каталогу.
- **Runtime verification:** 3 последовательных прогона `run-screens.ps1` PASS (exit 0); скриншот `09-clipart-picker.png` — все 10 элементов со значками (15685 байт против 7851 непрокрашенного до фикса).
- **Status:** FIXED

## ACC3-01

- **ID:** ACC3-01
- **Severity:** P0 (инфраструктура приёмки)
- **Screen/flow:** `Read-HarnessLines` в acceptance-lib.ps1 — все драйверы
- **Reproduction:** Любой таймаут ожидания строки stdout. Наивная версия вызывала `ReadLineAsync()` заново на каждой итерации; при таймауте ожидающая задача оставалась активной, и СЛЕДУЮЩИЙ вызов падал «Поток в настоящее время используется предыдущей операцией потока» — драйвер терял все дальнейшие доказательства.
- **Expected:** Таймаут одного ожидания не разрушает канал.
- **Actual:** IOException на следующем чтении; сценарий no-address остановился на первом же таймауте (журнал 15:57:19).
- **Evidence:** `noaddress-failure-evidence.md` (первый прогон), текст исключения в журнале.
- **Root cause:** Незавершённая задача чтения не сохранялась между вызовами.
- **Changed files:** `acceptance-lib.ps1` (`Read-HarnessLines` + `PendingTask` в результате `Start-Acceptance`).
- **Fix:** Незавершённая задача хранится в `$h.PendingTask` и подхватывается следующим вызовом; таймаут возвращает False, не прерывая операцию над потоком.
- **Regression test:** runtime — все 5 драйверов × 2 shells PASS; сценарий no-address проходит полностью (до фикса падал).
- **Runtime verification:** 10/10 прогонов exit 0.
- **Status:** FIXED

## ACC3-03

- **ID:** ACC3-03
- **Severity:** P1 (инфраструктура приёмки)
- **Screen/flow:** harness (UiAcceptance) — необработанные исключения потока UI
- **Reproduction:** Любое необработанное исключение на UI-потоке (например, UX3-01) показывает МОДАЛЬНЫЙ диалог ThreadException: поток блокируется навсегда, драйвер не получает ни stdout, ни выхода — приёмка виснет до watchdog. Оставшийся процесс UiAcceptance (PID 119900, живой 48 минут с открытым диалогом) был найден и завершён — это собственный процесс данного сеанса (профиль-зонд Picket302Probe).
- **Expected:** Незавершённая приёмка fail-closed: диагностика в stderr и код возврата, без модалов.
- **Actual:** Модальный диалог; процесс переживал остановку драйвера только через taskkill.
- **Evidence:** Диалог JIT-отладки с текстом исключения (зафиксирован оператором); зависший PID 119900.
- **Root cause:** WinForms по умолчанию показывает ThreadException-диалог; harness не переопределял режим.
- **Changed files:** `tools/ui-acceptance/Program.cs` (`SetUnhandledExceptionMode(ThrowException)` + комментарий-регрессия).
- **Fix:** Исключение пробрасывается из цикла сообщений в верхний try/catch harness: stderr-диагностика, код 1, гарантированная очистка профиля.
- **Regression test:** Static: невозможно; runtime-условия драйверов «harness exit 0»/«дерево чисто» ловят обратный случай.
- **Runtime verification:** 3× screens + 5×2 drivers PASS после фикса.
- **Status:** FIXED
