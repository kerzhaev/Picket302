# DPI 125 % / 150 % (stage3.1, 2026-11-08)

## Статус: симуляция, не OS-DPI

Общесистемный масштаб host-машины не менялся (запрещено менять настройки
машины). Проверка выполнена через **реальный конвейер WinForms PerMonitorV2**:
формам отправляется `WM_DPICHANGED` (SendMessageW, WPARAM=120/144/96,
LPTR=suggested rect) — WinForms сам перемасштабирует шрифты, контролы и
позицию. Harness переведён на `ApplicationHighDpiMode=PerMonitorV2`
(был SystemAware: `WmDpiChanged` применял только suggested-прямоугольник без
рескала контролов — DeviceDpi оставался 96; дефект механизма симуляции
найден и исправлен в этой серии).

```
DPI_RUNTIME_125_VERIFIED=NOT_RUN_ON_HOST   (OS-стенда нет)
DPI_RUNTIME_150_VERIFIED=NOT_RUN_ON_HOST
DPI_SIMULATION_125_VERIFIED=true           (dpi-report ниже)
DPI_SIMULATION_150_VERIFIED=true
```

накопление давало строки чужих форм — регрессия драйвера исправлена).

## Найдено в ходе проверки

1. **LAY3-01** (registered, P2): переполнение FlowLayoutPanel в строке TLP —
   воспроизводится на ВСЕХ масштабах, включая базовый 96 (вне-родителя=1 в
   LAYOUTCHECK на 96/120/144) — не DPI-дефект, а существующий дефект
   раскладки; DPI-критерии §8.3 на нём не валит (контрол присутствует и при
   100 %, поведение одинаковое).
2. При рескале suggested-rect центрируется от старых координат — формы
   могут выезжать за экран; драйвер возвращает окна в видимую область
   (SetWindowPos) — ограничения симуляции, не приложения.

## Что НЕ доказано

- Перекрытия/обрезания, видимые только при реальном OS-масштабе (рендеринг
  шрифтов, классические Win32-диалоги, системные меню).
- Экраны, не вошедшие в D1–D4 (печать, предпросмотр, клипарт) на других
  масштабах — следующая волна (OS-DPI стенд 125/150 %).
