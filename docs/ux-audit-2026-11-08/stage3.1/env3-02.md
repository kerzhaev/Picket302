## 3. Поиск кодовых путей, пишущих в профиль (§6.2)

Проверено: `GetFolderPath(ApplicationData)` (15 мест), `connection.json`,
`MarkConnectionEstablished`, `КаталогДанныхПоУмолчанию`, конструкторы
`ConnectionManager` / `ServerRegistry` / `LogHub` / `LicenseStore` /
`DpapiSecretStore`. Итог:

- Вся цепочка AppServices → `ConnectionManager(профиль.ConnectionSettingsPath, …)`
  — ЯВНЫЙ путь профиля; fallback на production отсутствует.
- `MainShell.ИнициализироватьAsync` вызывает `MarkConnectionEstablished` →
  `СохранитьНастройки()` — пишет ТОЛЬКО в путь, переданный конструктору
  (в acceptance — изолированный).
- Найден ТЕОРЕТИЧЕСКИЙ обход вне профиля: `MainShell.ОткрытьБазу`
  (MainShell.cs:2055) и скрытый вход Program.Main создают
  `new ConnectionManager()` без пути → production
  `%AppData%\Picket302\connection.json`. Это ПРЕДНАМЕРЕННОЕ
  производственное поведение (диалог подключения всегда к реальному
  профилю), в acceptance-сценариях диалог «Подключение к базе данных»
  драйвером не открывается — обход в прогонах не достигается.
  **Владельцу**: если нужно жёсткое запрещение — передавать явный путь и в
  этих двух точках (отдельное решение, не выполнено без запроса).
- Найден и ЗАКРЫТ реальный обход реестра: `AppServices` строит
  `CompositeCurrentSenderStore`, который на `Write` пишет SenderId и в
  `HKCU\Software\PEPro\CurrentSender` — РЕАЛЬНУЮ машину, вне любого
  профиля. Каждый acceptance-сеев отправителя (printflow/noaddress/
  screens/screen2/noprinter/dpi) писал синтетический идентификатор в
  реестр пользователя. Исправление — см. §4.

## 4. Контейнирование (исправления этой серии)

1. **Изоляция реестра отправителя**: `AppServices.СоздатьAsync` получил
   параметр `реестрОтправителяИзолирован`; при нём вместо
   `WindowsCurrentSenderRegistryStore` используется новый
   `NullCurrentSenderStore` (чтение null, запись no-op). Harness передаёт
   `true` во ВСЕХ режимах. Производственное поведение не изменено
   (флаг по умолчанию сохраняет реестр).
2. **Журнал profile-sensitive операции**: harness печатает
   `GUARD PASS pid=<PID> root=<корень> process=<путь>` в stdout каждого
   прогона — связь «прогон ↔ процесс ↔ корень» теперь есть в каждом
   evidence-файле (§6.3).
3. **Regression-тесты**: `ContainmentIsolationTests` (5 кейсов, Debug+Release
   PASS) — подменённый принтерный менеджер, дефолтный менеджер равен
   прямому winspool-чтению, реестр не пишется при SetGlobalSender,
   реквизиты подключения живут только в явном пути профиля, контракт
   NullCurrentSenderStore.

## 5. Доказательство контейнирования

- Вся батарейка серии (8 драйверов × PS 5.1/PS 7, happy + 8 fault-инъекций
  screens2): production delta 0/0/0 в каждом прогоне, sentinel совпал.
- `HKCU\Software\PEPro\CurrentSender\SenderId` = ABSENT **до и после всей
  батарейки** — раньше каждый прогон писал туда синтетический Id.
